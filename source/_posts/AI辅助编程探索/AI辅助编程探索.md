# AI辅助开发大型项目管理框架

## 一、项目是什么

**ClaudeDevKit** 是一个专为 AI 编程助手设计的项目治理框架。

**一句话概括**：让 AI 在帮你写代码的同时，不会乱改你的核心代码、不会破坏你的 API、不会忘记当前在做什么任务。

### 解决的问题

| 痛点 | 场景 | ClaudeDevKit 的解决方案 |
|------|------|------------------------|
| 代码被乱改 | AI "顺手"修改了核心模块导致崩溃 | 三级文件保护机制 |
| API 被破坏 | AI 改了接口参数，调用方全挂 | Breaking Change 自动检测 |
| 状态混乱 | 每次新会话都要重新解释项目 | PROJECT.md 统一状态管理 |
| 提交不规范 | AI 生成的 commit message 看不懂 | Conventional Commits 自动生成 |
| 目标跑偏 | AI 改着改着就偏离了当前任务 | 目标追踪系统 |

### 失败场景：没有 ClaudeDevKit 会怎样

| 缺失的机制 | 失败场景 | 后果 |
|------------|----------|------|
| **没有目标追踪** | AI 在多个模块之间"游走"，改完 A 又去"优化" B | 任务碎片化，主目标迟迟无法完成 |
| **没有保护机制** | AI 在 refactor 时"顺手"重构了核心模块 | 稳定代码被破坏，引入难以排查的 bug |
| **没有 API 检测** | Breaking Change 被默默引入，无人知晓 | 上线后调用方大面积报错 |
| **没有状态管理** | 每次新会话都要重新解释项目背景 | 大量时间浪费在重复沟通上 |
| **没有提交规范** | commit message 是 "fix bug"、"update code" 这类废话 | 无法追溯变更原因，回滚困难 |

**典型翻车案例**：

```
用户：帮我优化一下用户模块的性能
  │
  ▼
AI：好的，我优化了数据库查询...
    顺便重构了认证逻辑...
    还清理了一些"冗余"代码...
  │
  ▼
结果：
  • 用户模块确实快了 20%
  • 但认证系统崩了（那不是冗余代码）
  • 而且 API 参数被改了，前端全挂
  • commit message: "optimize user module"
```

**ClaudeDevKit 的防护**：

```
用户：帮我优化一下用户模块的性能
  │
  ▼
AI：好的，我优化了数据库查询...
  │
  ▼
/commit 时触发检查：
  ✓ 用户模块是 active，允许修改
  ✗ 认证模块是 core，禁止修改 → 阻止
  ✗ API 参数变更检测 → Breaking Change 警告
  │
  ▼
结果：
  • 用户模块优化完成
  • 核心代码安然无恙
  • API 变更被记录，需用户确认
  • commit message: "perf(user): optimize database queries"
```

## 二、核心设计理念

### 极简但可控

- **极简**：8 个文件实现完整治理能力
- **可控**：三级保护 + API 保护 + 目标追踪

### 以 Git 提交为驱动

整个框架的自动化流程围绕 `/commit` 命令展开。每次提交时自动执行：

```
代码检查 → 文件保护检查 → API 变更检测 → 目标进度检查
    ↓
生成规范提交信息 → 执行提交 → 自动更新项目状态文件 → 记录详细历史
```

## 三、核心机制

### 3.1 三级文件保护

这是框架最核心的机制。通过在 PROJECT.md 中定义模块等级，控制 AI 的修改权限：

| 等级 | 含义 | AI 修改规则 |
|------|------|-------------|
| `active` | 活跃开发中 | 自由修改 |
| `stable` | 已稳定 | 需用户确认后才能修改 |
| `core` | 核心模块 | 禁止 AI 自动修改 |

**工作原理**：当 AI 执行 `/commit` 时，会自动检测变更文件所属的模块等级，根据等级决定是放行、询问还是阻止。

### 3.2 API 契约保护

针对 API 相关文件（routes、controllers、endpoints 等），自动检测是否为 Breaking Change：

| 变更类型 | 是否 Breaking | 处理方式 |
|----------|---------------|----------|
| 删除 API 路径 | 是 | 需确认 |
| 删除/修改参数 | 是 | 需确认 |
| 参数类型变更 | 是 | 需确认 |
| 新增可选参数 | 否 | 放行，提示更新文档 |

### 3.3 目标追踪

采用**单一焦点模式**：一次只有一个主目标。

- AI 每次提交都会询问：当前目标是否完成？
- 完成后提示设置下一个目标
- 目标状态自动同步到项目文档

### 3.4 项目拆解与任务划分

这是框架实现"AI 可控"的关键设计。

**问题**：大型项目动辄上百个文件，AI 的上下文窗口有限，如何让 AI 既能快速理解项目全貌，又能专注于当前任务？

**解决方案**：通过文件结构实现"全局视野 + 局部专注"的平衡。

#### 两层视图设计

| 视图 | 文件 | 内容 | 作用 |
|------|------|------|------|
| **全局视图** | PROJECT.md | 模块列表、状态、保护等级 | 30 秒内了解项目全貌 |
| **当前焦点** | CURRENT_GOAL.md | 单一目标、进度、相关文件 | 专注执行当前任务 |

#### 工作原理

```
新会话开始
    │
    ▼
/readproject  ────→ 读取 PROJECT.md
    │               • 看到所有模块
    │               • 知道哪些是 core/stable/active
    │               • 了解项目整体架构
    │
    ▼
/goal  ───────────→ 读取 CURRENT_GOAL.md
    │               • 聚焦单一任务
    │               • 知道要改哪些文件
    │               • 不被其他模块干扰
    │
    ▼
[AI 专注执行当前任务]
```

#### 模块拆分原则

PROJECT.md 中的模块定义遵循以下原则：

| 原则 | 说明 |
|------|------|
| **独立性** | 每个模块有明确的边界和职责 |
| **可追踪** | 每个模块有独立的状态（todo/dev/done） |
| **可保护** | 每个模块有独立的保护等级（active/stable/core） |
| **粒度适中** | 不太大（难以管理），也不太小（过于碎片化） |

#### 对比传统方式

| 维度 | 传统方式 | ClaudeDevKit 方式 |
|------|----------|-------------------|
| 项目理解 | AI 需要遍历大量文件 | PROJECT.md 一览全局 |
| 任务聚焦 | AI 容易"顺手"改其他模块 | CURRENT_GOAL.md 限定范围 |
| 上下文消耗 | 每次都要重新解释项目 | 文件即文档，持久化状态 |
| 协作效率 | 人要反复说明"不要改这个" | 保护等级自动生效 |

**核心价值**：让 AI 在有限的上下文窗口内，既能"看见森林"（项目全貌），又能"专注种树"（当前任务）。

## 四、命令系统

框架提供 4 个命令，覆盖 AI 辅助开发的全流程：

| 命令 | 用途 | 使用场景 |
|------|------|----------|
| `/readproject` | 读取项目概览 | 新会话开始时，让 AI 快速了解项目状态、模块、目标、历史 |
| `/ask` | 只读问答 | 安全地分析代码、排查问题，AI 只能读不能改 |
| `/goal` | 目标管理 | 设置/查看/完成当前开发目标 |
| `/commit` | 规范化提交 | 核心命令，触发完整治理流程 |

### `/commit` 命令详解

这是框架的核心命令，完整流程：

1. **Pre-commit 检查**：执行 lint，失败则停止
2. **清理临时文件**：删除缓存、日志等无关文件
3. **文件保护检查**：根据模块等级决定放行/确认/阻止
4. **API 变更检测**：如有 API 变更，检测 Breaking Change
5. **目标进度检查**：询问当前目标是否完成
6. **生成提交信息**：Conventional Commits 格式，包含完整变更内容
7. **执行提交**
8. **自动更新状态**：PROJECT.md、CURRENT_GOAL.md、ROADMAP.md
9. **记录 Git 历史**：history.md 摘要 + 详细日志文件
10. **Push**

## 五、Skills 模块

Skills 是可复用的治理模块，被 `/commit` 命令调用：

| Skill | 职责 | 触发条件 |
|-------|------|----------|
| `workspace-governor` | 文件保护 | 所有文件变更 |
| `api-governor` | API 契约保护 | API 相关文件变更 |
| `goal-tracker` | 目标进度追踪 | 所有提交 |

## 六、项目结构

```
.claude/
├── PROJECT.md           # 核心：项目配置（模块定义、保护规则、历史）
├── commands/            # 命令定义
│   ├── readproject.md
│   ├── ask.md
│   ├── goal.md
│   └── commit.md
└── skills/              # 治理模块
    ├── workspace-governor.md
    ├── api-governor.md

docs/
├── ROADMAP.md           # 项目路线图
├── CURRENT_GOAL.md      # 当前目标
├── api/API.md           # API 文档
└── git/                 # Git 历史系统
    ├── history.md       # 提交摘要
    └── logs/            # 详细日志
```

## 八、总结

ClaudeDevKit 的核心价值：

| 维度 | 传统 AI 辅助开发 | 使用 ClaudeDevKit |
|------|------------------|-------------------|
| 代码安全 | AI 可能乱改核心代码 | 三级保护，核心代码安全 |
| API 稳定 | 变更无感知 | Breaking Change 自动检测 |
| 项目状态 | 每次会话都要重新解释 | PROJECT.md 统一管理 |
| 提交规范 | 依赖 AI 自觉 | 强制 Conventional Commits |
| 开发焦点 | 容易跑偏 | 目标追踪，保持专注 |
| **上下文效率** | **AI 需要遍历大量文件** | **全局视野 + 局部专注** |

**核心创新**：
1. **项目拆解**：通过 PROJECT.md 的模块定义，让大型项目变成可管理的单元
2. **任务聚焦**：通过 CURRENT_GOAL.md，让 AI 专注当前任务，不被其他模块干扰
3. **以 Git 提交为驱动**：所有自动化围绕 `/commit` 展开，无需额外操作

这套设计让开发者既能享受 AI 的效率提升，又能保持对项目的完整控制——**AI 看得见全貌，但只动该动的地方**。
